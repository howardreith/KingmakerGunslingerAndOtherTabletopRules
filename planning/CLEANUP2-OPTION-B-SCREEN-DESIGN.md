## Historical one-PC-screen proposal, 2026-10-22

The sections below retain the original interaction and engine-contract design.
Their references to a first screen or later approval describe that proposal's
scope at the time, not a current instruction to leave ordinary surfaces unfinished.

## Screen and player interaction

Scope one screen: the **desktop action bar Spells tab for the selected player
character**, with an Elementals chooser opened from that tab. It presents a
common family without claiming that the underlying spells are interchangeable.
Its launch tile is presentation state, not a new BlueprintAbility, known spell,
prepared slot, saved hotbar object or castable parent.

Inside the chooser:

1. Pick rank (Small II, Medium IV, Large V, Huge VI, Greater VII, Elder VIII).
   Only ranks with an actual source on this character appear; an exhausted
   source can remain visible with its native disabled reason.
2. Pick a family-first row, for example **Elemental, Fire, Small**. Use the
   existing approved canonical presentation for this face of the chooser.
3. Pick an explicit **Cast using** source. Nothing is cast by selecting a
   creature or source. With one eligible source, show that source selected and
   still display its identity and cost.
4. **Cast** hands that exact existing source's native selected-child invocation
   to the normal targeting/action pipeline. Cancel closes the chooser without
   choosing an ability. Resource and availability state refresh immediately
   before handing it over; a stale/disappeared source refuses that selection.

Example, only when this character actually possesses both sources:

| Visible source choice | Cost shown | Execution |
| --- | --- | --- |
| Summon Monster II · Wizard | Wizard II: 1 matching Summon Monster II preparation | Its existing canonical Fire/Small execution child, original Wizard source and metamagic |
| Summon Small Elemental · Wizard | Wizard II: 1 matching Summon Small Elemental preparation | Its original native Small Fire child, original standalone source and metamagic |

These are two distinct source choices under one species row. Do not silently
prefer either, combine them into a numerical total or use one when the other
becomes exhausted. Two different spellbooks produce two visibly named choices.
Metamagic versions remain distinct choices with actual adjusted level/action
cost. The source tooltip must retain native descriptors and rules; the common
species title cannot replace it.

This first chooser admits only the same-rank **One-creature** choices. Higher
SM/SNA tiers' 1d3 and 1d4+1 elemental branches retain their native presentation
and original higher-tier source. Grouping by elemental rank never changes a
quantity, chooses a lower slot or moves those branches into this first scope.

The exact standalone Small parent is `970c6db48ff0c6f43afc9dbb48780d03`, its Fire
child `d8f88028204bc2041be9d9d51f58e6a5`; canonical SM II is
`1724061e89c667045a6891179ee2e8e7`. SNA II

## Backing records and invocation

Each displayed source is backed by the real native source row/AbilityData and
the child generated by that source's existing conversion/variants path. A
transient presentation record holds references to:

- current caster and the existing source MechanicActionBarSlot/AbilityData;
- original source book, Fact/SourceItem, metamagic and source chain;
- original native selected-child AbilityData/blueprint and ParamSpellSlot where
  supplied by that native route;
- actual current known/prepared availability and displayed spell level.

It does not manufacture a canonical child for a standalone source, assign an
arbitrary ConvertedFrom, reparent shared blueprints or mutate the original
objects. The stable grouping key is an exact allowlisted rank/element identity;
the invocation key includes the real actor, source, child, book and metamagic.
Names alone never merge records. Unknown children or a changed conversion graph
stay in their original native row.

The installed 2.1.7b engine contract, audited in
[CLEANUP2-ELEMENTAL-CONTRACT-AUDIT.md](CLEANUP2-ELEMENTAL-CONTRACT-AUDIT.md), makes
this distinction necessary:

- selected `AbilityData.Blueprint` owns executed actions, descriptors, ranks,
  targeting, restrictions and selected resource logic;
- native `ConvertedFrom` retains the original source and delegates spellbook
  availability and spending back through it;
- original Fact/metamagic and item charges remain meaningful;
- `ParamSpellSlot` is retained, but native `Spellbook.SpendInternal` matches an
  available preparation; it does not use that field as an unconditional exact
  slot-index debit. The screen therefore promises the original source's
  matching native preparations, not a fungible pool of every prepared spell
  at that level or a forcibly selected duplicate slot index.

Preparation stays in the existing spellbook screen. For prepared books this
chooser can consume only real existing matching source preparations; it cannot
prepare, learn, convert another spell into a new source, alter a spell level or
borrow a different book's remaining pool. For spontaneous books, a source must
actually be known and
native `CanSpend` must permit its own level pool. A source that is known but
exhausted can be shown disabled with its native reason, never replaced by a
different source behind the same click.

## Why source identity stays visible

The retained native diagnosis found zero equivalent parent/child pairs. The
standalone elemental descriptors (Electricity, Acid, Fire, Cold), canonical SNA
caster-alignment/AfterSpawn changes, SM conditional/spawn-buff differences and
native versus project unit definitions have not been reconciled. Actor-specific
specialization, metamagic/rod and KMG Elemental Insight/Acadamae rules can also
distinguish sources. Grouping does not waive those differences. See
[CLEANUP2-ELEMENTAL-RULES-PROPOSAL.md](CLEANUP2-ELEMENTAL-RULES-PROPOSAL.md) for
the exact 24-child dispositions and rank GUIDs.

The common chooser could consolidate repeated ordinary **standalone elemental
parent** tiles only in this one transient tab, after every actual source/child
route from each consolidated tile is represented and the record/dispatch
contract is proved. The mixed-creature canonical SM/SNA parent tiles remain
intact: they also expose other creatures and quantities. No child is removed
from those parents to force one exclusive discovery location.
Existing pinned/prepared/known objects remain intact and native buttons remain
usable. This provides a concrete presentation reduction while leaving duplicate
learning/list entries unresolved. No global `GetSpells`, Hidden flag, spell-list
publication or serialized action-bar rewrite belongs to this design.

## Native implementation seam and remaining proof

The existing PC ActionBarSpellsGroup fills exact native child slots from one
source, with exact source/child references already observed by Cleanup 2 menus
and tooltips. It does **not** itself prove a mixed-source group: a common
multi-source chooser requires a new presentation controller which retains and
dispatches each original native row mechanism. Reusing a canonical group and
merely swapping icons/ConvertedFrom is not an approved shortcut.

Before implementation, verify the exact native click/targeting handoff for a
retained source MechanicSlot, including source-row lifetime while its native
group is closed. If the mechanism cannot outlive that group safely, recreate
the original source group through its native method at dispatch and select its
exact child by identity. That alternate still needs native ownership and cost
proof; it is not assumed feasible. If neither preserves the native context,
retain ordinary source rows on this screen as the explicit exception.

Module OFF, character/book changes and view reconstruction destroy only the
owned transient chooser. The unmodified native tab repopulates from its source
objects. A foreign replacement of the tab/rows invalidates the chooser; teardown
does not repair or overwrite somebody else's UI. No stored adapter survives a
save or requires a migration.
